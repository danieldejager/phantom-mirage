# Decoy realism: acceptance criteria (draft v0.1)

Status: design only. No probing happens until the owner approves a test. Every test below runs only against decoys inside `192.168.1.240/29`, from the attacker VM, and each command is posted in the project room as it is run.

## Goal and bar

The goal is that a decoy survives standard scanning and fingerprinting and looks like a real host of its persona. The bar is not "fool proof". A determined human with time and a real client can usually tell a low-interaction decoy from a real host. This document defines what we can prove, and states the limit.

A persona passes only if every test in its section passes. One failed test fails the persona.

## Definitions

- Persona: one decoy host identity (for example Linux web server, Windows file server, Windows SQL server) with its own address, open ports, service responses, OS fingerprint and MAC address.
- Consistent: every observation agrees with the persona's claimed OS and role.

## A. Port and service consistency (each persona)

| ID | Criterion | Measure | Pass |
|----|-----------|---------|------|
| A1 | Open ports match the persona's role | Full TCP scan, ports 1-65535 | Open set equals the persona's documented list, nothing else |
| A2 | No impossible port mix | Review of A1 output | No Windows-only service (SMB, RDP, MS-SQL, WinRM) on a Linux persona, and no Linux-only service (OpenSSH with Ubuntu string) on a Windows persona |
| A3 | Service detection agrees with the persona | `nmap -sV` | Every open port is identified as the persona's service and version, with no `?` (unrecognised) result |
| A4 | Real client completes the handshake | Real clients: `ssh`, `ftp`, `curl`, `smbclient`, an RDP client, `sqlcmd` or equivalent | Each client completes its protocol handshake and reaches the authentication step. A client that errors on a malformed or missing handshake fails the port |
| A5 | Authentication failures look real | Wrong-password attempts per service | Real error text and codes for that service, same response to a bad user and a bad password where the real service does the same |
| A6 | TLS looks real | `openssl s_client`, `nmap --script ssl-cert,ssl-enum-ciphers` | Valid handshake, plausible certificate (sensible subject, validity period and key size, not self-evidently generated by the tool), and cipher support that matches the claimed OS and software version |
| A7 | Version strings are current and patched | Compare banners against the vendor advisories for the claimed version | No string that matches a known-vulnerable build, including the OpenSSH revision for the claimed Ubuntu release |

## B. OS and network stack fingerprint (each persona)

| ID | Criterion | Measure | Pass |
|----|-----------|---------|------|
| B1 | OS detection agrees with the persona | `nmap -O --osscan-guess` against an open and a closed port | Top guess is the claimed OS family, and no guess of a different family above 50 percent. Needs admin rights on the attacker VM |
| B2 | TTL matches the claimed OS | Capture or `nmap --reason` | Initial TTL 64 for Linux, 128 for Windows, with the hop count accounted for |
| B3 | TCP options and window size match | `nmap -O` details and packet capture | SYN-ACK options, window size and timestamp use match the claimed OS |
| B4 | Closed ports behave like the claimed OS | Connect to closed ports and to a UDP closed port | TCP reset on closed ports. For UDP, ICMP port unreachable at a plausible rate. Linux and Windows differ, and the persona must match its own |
| B5 | ICMP behaves like the claimed OS | `ping`, `nmap -PE -PP -PM` | Echo reply matches. Timestamp and netmask replies match the claimed OS (Windows and Linux differ) |
| B6 | IP ID and sequence behaviour match | `nmap -O` sequence section | IP ID and TCP ISN class match the claimed OS |

## C. Link layer and identity (across personas)

| ID | Criterion | Measure | Pass |
|----|-----------|---------|------|
| C1 | Each persona has its own MAC address | `arp -a` after contact, packet capture | Each persona address resolves to a different MAC, none shared with the sensor's own address |
| C2 | MAC vendor matches the persona | OUI lookup | A plausible vendor for the persona (a VM, server or workstation maker), not a vendor that contradicts the claimed role |
| C3 | Reverse DNS and NetBIOS names are plausible | `nslookup`, `nbtstat -A`, `nmap --script nbstat` | Consistent hostnames and domain or workgroup names across the hosts, and no name containing the product name |
| C4 | No telltale of the sensor | Review of banners, pages, error text, TLS subject | No string naming the product, the sensor, or a honeypot tool |

## D. Timing and behaviour

| ID | Criterion | Measure | Pass |
|----|-----------|---------|------|
| D1 | Latency is plausible | 100 pings and 100 connect timings per persona | Median within a plausible range for the claimed hardware and no more than 2 ms apart from the sensor's own responses for a same-segment host. Variance is non-zero (real hosts jitter) |
| D2 | Response timing differs by service, as it does on real hosts | Timed handshakes | No identical response time to the millisecond across ports or personas |
| D3 | Behaviour under load is realistic | 200 connections in 10 seconds to one port | No instant refusal of all connections, no crash, and a plausible limit or slowdown |
| D4 | Idle and session behaviour | Hold a connection open for 5 minutes | Idle timeout matches the real service default |
| D5 | Stability | 24 hours of scanning at a moderate rate | No persona stops answering, changes its fingerprint, or leaks an error |

## E. Operational safety

| ID | Criterion | Measure | Pass |
|----|-----------|---------|------|
| E1 | Decoys answer only for their own addresses | Probe the range's unused and used addresses with the owner's explicit approval and a disposable test host | No answer for any address outside the persona map, and no ARP reply for an address owned by a real device |
| E2 | Detection works | Trigger each persona with a scan and a login attempt | Each event is logged with persona, source and time |
| E3 | Logs do not leak to the attacker | Review of outbound traffic and responses | Nothing from the log or console is reachable from the decoy addresses |

## F. Limit and residual risk (to be accepted by the owner)

- A real client that uses a rare or deep protocol feature can expose a low-interaction emulator. This is the largest residual gap and is why real-service sandboxes or proven emulators matter more than custom code.
- A host on the same segment can read ARP and timing at a depth that statistical tests catch. D1 and C1 reduce this, they do not remove it.
- Persona drift: patched version strings go out of date. Re-check A7 on every release.
- None of these tests can prove an attacker will not guess. The honest claim is: it passes the tests above.

## Test order when approved

1. A (service) and B (stack) on one Linux persona, then one Windows persona.
2. C (identity), then D (timing).
3. E1 only with an explicit owner approval and a disposable host.
4. Write-up in `docs/security-testing/` with each command and the time it was run, and an issue for anything that fails.
