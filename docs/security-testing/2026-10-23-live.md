## T0. Host discovery

**Command:**
```
nmap -sn -PE -PS22,80,443 192.168.1.240/29 -oA T0-discovery
```

**Fact:** All eight addresses `.240` through `.247` were up. Each reported MAC `00:1C:42:E8:27:0C` (Parallels / sensor NIC). Latency about 28 ms.

**Note:** An earlier `-PR` ARP-only discovery from this Windows session returned 0 hosts. That was a privilege limit on raw ARP from a non-admin session, not a product failure. ICMP discovery and `ping` both succeeded afterwards.

**Observation:** Network and broadcast addresses of the `/29` also answer. Confirm whether that is intentional.

## T1. Common TCP ports on all decoys

**Command:**
```
nmap -Pn -sT -p 21,22,23,25,80,110,135,139,443,445,502,3389,5900,8080,8443 -T4 --open -oA T1-tcp-common 192.168.1.240/29
```

**Fact:** With `--open`, nmap reported no open ports on any of the eight hosts (13.71 s).

**Expected (from console design):** decoys should present device-type ports (for example Windows server, Siemens PLC, printer). Port `8443` should stay closed on decoys. Port `22` on decoy addresses should be dropped by the console firewall.

**Inference:** farpd is answering ARP/ICMP, but phantom-mirage is not presenting TCP listeners on these common ports from this attack host. Either no templates with those ports are loaded, TCP replies are filtered, or the daemon is not serving TCP on the decoy block.

**Recommendation:** On the sensor, confirm `phantom-mirage` is running, the conf lists templates with open ports, and capture traffic while repeating T1. Track as a product finding until a decoy shows at least one intentional open TCP port.

## T2. Console and SSH exposure on the sensor LAN address

**Command:**

```
nmap -Pn -sT -p 22,80,443,8443,3389 -T4 -oA T2-sensor 192.168.1.112
```

**Fact:**
- `8443/tcp` closed (good: console must not listen on the LAN)
- `22/tcp` closed from this host

**Pass criteria for console:** met for T2 (`8443` not open on LAN).

**Note on SSH:** Operator access is supposed to be SSH to the sensor. Closed from this Windows VM may mean sshd is bound elsewhere, firewalled, or not running. Confirm from the Mac tunnel host. Not scored as a failure until that check is done.
